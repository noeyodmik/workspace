정연홍

기본급만 존재하는 것이 아니라, 수당, 회비, 시간외수당 등과 같은 항목들에 대해서도 관리가 필요하다. 특히 직접 입력이 아닌 별도의 기준에 따라 자동으로 계산되어 반영되기도 원한다. 

Chapter 7. 간접 평가, 수당관리, 회비 

▶ Overview
급여를 지급하기 위해서는 단순히 기본급만으로 처리되지 않는다. 각종 수당, 공제 항목들이 존재한다. 수당들은 정기적으로 일정한 금액이 지급되는 경우도 있고 비정기적으로 지급되는 상여와 같은 항목들도 있다. 공제 역시 마찬가지다. 

모든 임금 항목에 대해서 담당자가 금액을 직접 입력하는 것도 비효율적이고, 부정확한 금액이 반영될 수도 있다. 그런 경우에 시스템에서 기준에 대한 설정을 통해서 관련된 금액이 자동으로 계산되어 금액을 반영해주는 편의성도 필요하다. 

이번 장에서는 수당, 수당에 대한 자동 반영, 기타 수당과 유사한 항목들에 대한 설정에 대해서 설명할 것이다. 회사 내에서 수당/공제 항목이 신설된 경우 이번 장을 통해서 손쉽게 설정을 할 수 있다고 생각된다. 

Chapter 6을 통해서 임금 유형 자체 생성과 기본적인 설정에 대해서는 이미 숙지가 되어 있을 것이다. 기본급 설정을 잘 이해하고 있다면 사실상 이번 장은 이미 절반은 다 이해했다고 봐도 무방하다. 많은 부분의 설정이 같은 관계로 중복하여 설명하지 않았다. 특화된 부분에 대해서만 설명을 하였고, 이해하면 된다. 특히 수당 관리 부분에서 지급 모델에 대해서 이해하는 것이 중요하다. 


1. 간접 평가
▶ 목적
인사관리 이하의 급여 데이터 IMG의 경우는 급여 관련 인포타입의 설정이나 임금 유형에 대해 설정하는 곳이다. 그러한 데이터들은 일반적으로 사용자가 직접 입력을 해야 한다. 임금 유형이나 해당 금액이나 그러한 데이터를 직접 입력하지 않고, 기 입력된 해당 사원의 조건이나, 혹은 임금 유형만 입력하게 되면, 조건에 맞게 시스템 내부적으로 관련된 데이터, 혹은 금액을 제시해주는 방식을 '간접 평가'라고 한다. 

▶ IMG Path
인사관리 -> 인사관리 -> 급여 데이터 -> 간접 평가

1.1 간접 평가 모듈 생성

▶ IMG 화면

<그림> 7.1 간접 평가 모듈생성 IMG 메뉴
　　　
▶ IMG Path
인사관리 -> 인사관리 -> 급여 데이터 -> 간접 평가 -> 간접 평가 모듈 생성

'Caution : The table is cross-client' 라는 메시지가 나오게 된다. SAP는 IMG라는 개념을 통해서 전체적인 프로세스를 제어하는 기준값을 관리한다. 프로그램도 역시 소스를 테이블에 저장한다. IMG로 설정하는 값은 해당 클라이언트별로 저장된다. 프로그램의 경우는 해당 서버에 공통으로 적용된다. 예를 들어 개발서버에는 100번 클라이언트와 200번 클라이언트가 있다고 하면, IMG는 100번과 200번에 각각 적용해야 하지만, 프로그램은 100번에서 저장을 하게 되면 200번에서도 동일하게 조회가 된다. 이런 프로그램과 같은 방식을 Cross-client라고 한다. IMG와 같은 적용방식을 client-independent라고 이야기한다. 하지만, IMG 메뉴가 모두 client-independent 속성은 아니다. 간접 평가 모듈 생성 부분은 cross-client이다. 


<그림> 7. 2 간접 평가 모듈 관리 화면

간접 평가 유형별 의미와 실제 사용 예시를 들어보도록 하겠다. 

▶ ANSAL

<그림> 7.3 Infotype0008(기본급) 연봉 필드 내역

Infotype 0008(기본급) 화면의 연봉 필드에 나타나는 금액을 산출하기 위한 간접 평가이다. 이후 단계에서 설정하는 연봉 산정 임금 유형 부분에서 임금 유형 ASAL을 이용하여 화면에 출력하게 된다. 해당 임금 유형을 구성하는 임금 유형을 설정하고 ASAL의 간접 평가 속성이 ANSAL로 처리가 되어 Infotype 0008(기본급) 화면에 처리된다. 

▶ CONST
몇몇 임금 유형의 경우는 담당자가 직접 금액을 입력하는 방식이 아닌, 회사 내의 규정에 정해져 있는 금액으로 처리될 필요가 있다. 이 경우 해당 임금 유형별로 금액을 관리하여 담당자가 임금 유형을 생성 시에 자동으로 표시되도록 한다. 간접 평가의 경우에 모듈변형을 이용할 수 있다. CONST의 경우에 모듈변형 ' '인 경우는 테이블 T510K의 금액으로 관리하고, 'M'인 경우는 수 단위에 해당 수를 입력하면 T510K에 설정된 금액에 가산하여 처리된다. 'P'인 경우에는 수 단위에 해당 비율을 입력하면 T510K에 설정된 금액에 가산하여 처리된다. 


<그림> 7.4 임금 유형 4050(주거보조비1) 간접 평가 모듈 지정 내역

간접 평가 모듈이 CONST로 지정된 내역이다. CONST인 경우에 T510K에도 해당 임금 유형에 관련된 금액이 저장되어야 한다. 


<그림> 7.5 테이블 T510K의 임금 유형 4050 내역
테이블 T510K 에 해당 임금 유형의 금액을 기간별로 관리를 하여야한다.


<그림> 7.6 Infotype 0014(반복 지급및공제) 임금 유형 4050 입력 내역

해당 임금 유형의 간접 평가 모듈 속성이 CONST로 정해져있고, 테이블 T510K에 저장된 내역이 있는 경우에 그림1.7과 같이 해당 금액이 보여지게 된다. 

▶ PRZNT, SUMME, UNITS
특정 임금 유형의 경우는 다른 임금 유형의 금액을 이용하여 비율을 통해서 처리가 될 수 있다. 예를 들어 능력급의 경우는 기본급의 10%로 처리된다라면, 테이블 T539J에 능력급과 기본급을 연결하고 해당 능력급 임금 유형에 간접 평가 모듈을 지정을 하면 된다. 이때 PRZNT의 경우는 입력 화면에서 다시 한번 금액에 대한 조정이 가능하다. SUMME의 경우는 이미 T539J에 입력된 비율에 따라 처리된다. 


<그림> 7.7 테이블 T539J 임금 유형 4001 설정 내역

임금 유형 4001(능력급)은 연봉월액의 10%로 설정을 하였다. 모듈 지정을 PRZNT로 하여 infotype에서 입력시 다시 한번 변경이 가능하다. 


<그림> 7.8 Infotype 0014(반복 지급 및 공제) 능력급 입력 화면 

PRZNT로 설정한 임금 유형의 경우에는 수/단위로 입력을 하여 해당 금액을 간접 평가 처리한다. 연봉월액의 10%가 기준 금액이고, 수/단위에서 100으로 입력하면 10%의 금액이 그대로 들어오게 된다. 수/단위를 조절하게 되면 금액에 변동이 생긴다. SUMME의 경우는 금액의 변동이 없다. PRZNT, SUMME의 차이이다.

모듈 이름은 5자리로 되어 있고, Standard에서 제공하는 모듈들이다. 만약 추가로 사용자의 필요에 따라 만들고자 한다면 신규 엔트리를 선택해서 5자리 코드와 해당 설명을 모듈텍스트로 입력하면 된다. 사용자의 요구로 신규로 생성하는 경우는 모듈 이름의 첫 번째는 'Z', 'Y'를 사용해야 한다. 


1.2 간접 평가 모듈 생성
▶ IMG 화면

<그림> 7.9 BAdI: 간접 평가 모듈 유지보수 IMG 메뉴

▶ IMG Path
인사관리 -> 인사관리 -> 급여 데이터 -> 간접 평가 -> BAdI: 간접 평가 모듈 유지보수

간접 평가 모듈은 이미 정해져 있는 방식에 의해서 처리된다. 물론 사용자의 필요에 따라 만드는 경우에는 BAdI라는 것을 이용해야 하지만, Standard에서 제공하는 간접 평가 모듈의 로직을 변경하고자 한다면 이 부분을 활용해야 한다. BAdI라는 것을 이해하기 위해서 SAP라는 솔루션을 이해해야 한다. 솔루션이라고 하는 것은 특정 회사에 딱 맞는 맞춤복이 아닌 적당히 맞는 기성복에 개념에 가깝다. 그러한 기성복은 몸에 딱 안 맞을 수 있고, 넘치는 부분도 있을 것이다. 그런 부분을 적절하게 조정을 해주는 역할이 BAdI 혹은 User-exit이라고 한다. 물론 이러한 조정을 할 수 있는 부분이 모든 프로세스에 있는 것은 아니다. SAP에서 제공하는 부분 중에서도 몇 부분일 뿐이다. 만약 사용자가 수정하고 싶은 부분이 있지만, 그곳에는 BAdI, User-exit이 없다면 Standard 소스를 변경해야 할 것이다. 변경하고자 한다면 BC의 도움으로 해당 부분의 access key를 얻어서 변경해야 할 것이다. 


<그림> 7.10 간접 평가 모듈 'CONST'의 BAdI

유지보수 화면으로 들어가게 되면 위 그림이 나타나게 된다. 간접 평가 모듈인 'CONST'의 내역을 보여주고 있다. Attributes 탭은 해당 모듈의 내역을 보여주고, interface 탭에서 모듈의 로직을 수정할 수 있는 부분이 있다.


<그림> 7.11 간접 평가 모듈 'CONST'의 Interface 탭
Method라고 되어 있는 'DO_INDIRECT_VALUATION' 부분을 더블클릭하면, 해당 소스 내역으로 접근할 수 있다. 

2. 반복 지급 및 공제
▶ 목적
Infotype 0014(반복 지급 및 공제)에서 사용되는 임금 유형에 관련하여 설정하는 IMG이다. 

▶ IMG Path
인사관리 -> 인사관리 -> 급여 데이터 -> 반복 지급 및 공제


<그림> 7.12 반복 지급 및 공제의 IMG 메뉴 트리

변경사유정의, 임금 유형카탈로그 생성, 임금 유형그룹 '반복 지급 및 공제' 점검, 임금 유형텍스트점검, 인포타입별 허용 가능 엔트리 점검, 각PS 및 ESG에 대한 허용 가능 임금 유형 정의, 임금 유형특성점검, 1차 임금 유형에 대한 사원하위그룹 그룹핑 정의, 1차 임금 유형에 대한 인사하위영역 그룹핑 정의는 이미 6장 기본급에서 설명하였던 부분이다. 그룹핑 정의 부분을 제외하고는 같은 방식으로 설정하면 된다. 그룹핑 정의은 메뉴가 또 있지만, 사실상 기본급에서 했던 메뉴와 동일한 정보이다. 

추가지급(Infotype 0015), 추가지급: 비정기(Infotype 0267)의 경우도 마찬가지로 기본급에서 했던 방식대로 임금 유형을 생성하고, 추가적인 설정을 하면 된다. 이후에는 각 인포타입에서만 확인할 수 있는 메뉴에 대해서만 설명하도록 하겠다. 


<그림> 7.13 Infotype 0014(반복 지급 및 공제) 일반적인 화면

반복 지급 및 공제에서 다른 부분은 IMG메뉴상에는 '지급 모델'이라는 부분이 있다. 사실 한국급여에서는 지급 모델이 존재하지 않는다. 위 그림에서는 지급 모델을 넣는 부분이 없다. 임금 유형과 기간, 금액만을 입력하여 급여 계산 시에 사용된다.

일반적인 급여 계산에서 지급이나 공제는 특정 기간을 두고 처리를 한다. 하지만, 특정 항목의 경우는 두 달에 한 번씩 지급한다. 혹은 특정 월부터 지급하면 어떻게 처리를 할 것인가? 사실 이렇게 지급하는 경우는 극히 드물다. 혹시 모르니 설정 방법에 대해 설명하겠다. 

▶ 예 1) 매년 8월부터 격월로 지급하는 수당의 처리

<그림> 7.14 지급 일자를 이용한 지급 방법
<그림> 7.14에서 시작일은 2008.04.01부터 9999.12.31까지, 임금 유형 4017에 대해서 50,000원씩 지급하는 것으로 이해할 수 있다. 이 경우에는 매월 지급이 되지만, 지급일자 부분에서 첫 지급기간을 08로 입력을 하였다. 지급기간은 급여계산 기간과 같다고 생각하면, 08월부터 지급이 되는 것이다. 시작일과 무관하게 처리가 가능하다. 그리고 기간간격에 02로 입력을 하였기 때문에 2개월마다 지급하는 것이다. 

한국 급여에서는 지급 모델은 없지만, 지급일자를 이용하여 처리할 수 있다. 급여 계산 시에 Infotype 0014(반복 지급 및 공제)는 급여 Function인 P0014에서 해당 임금 유형이 해당 월에 지급 유무를 판단한다. 내부 로직에서 function 'RP_CHECK_PAY_PERIOD'을 통해서 지급일자 방식이나 지급 모델 방식으로 구분하여 해당 월 급여 지급 처리를 진행한다.

▶ 예 2) 매년 8월부터 지급을 하되, 8월, 11월, 12월만 지급을 하는 경우
지급일자의 경우는 정기적인 지급은 처리할 수 있다. 예 2)처럼 특정 월 이후 지급을 하되, 특정 월(규칙이 없는)에만 지급하는 경우는 문제가 다르다. 이런 경우에 지급 모델이 유용하게 대처할 수 있다.

① 지급 모델 정의
② 지급 모델의 지급(공제) 기간 정의
④ 지급 모델의 기본값 지정
④ 지급 모델의 기본값에 따른 임금 유형별 지급 모델 지정

위 순서대로 지급 모델에 대해서 설정을 하게 되면, 실제 Infotype 0014에서 사용하여 처리할 수 있다(물론 추가적인 화면 조정이 필요하다.).

화면조정에 대한 설명을 잠시 하고 다음 IMG 설명을 하겠다.

이렇게 입력된 프리미엄은 Infotype 2010(사원 지급 정보)에서 입력할 수 있어진다. 입력된 내역을 이용하여 급여 계산 시에 추가금액이나, 추가 수로 급여 계산을 할 수 있다. 하지만, 여기에서 한 가지 작업을 더 해주어야 한다.

Schema KR00의 경우에는 프리미엄 처리를 하려면, 두 가지 방법이 있다. 첫 번째는, 급여 계산 Rule인 XALQ를 schema KR00에 추가하여 이용하는 방법이 있다.


<그림> 7.33 Rule XALQ 내역
Rule에서는 테이블 T510P에 있는 금액 필드(BETRG) 값을 IT의 비율 필드(RTE)에 전송한다. 이후 Rule에서 가산되는 방식으로 처리해야 한다. 하지만, P2010이라는 function에 Standard는 Rule을 Par1 값으로 설정해두었다. Rule을 진행하게 되면 프리미엄 값이 IT 내역에 존재하지 않기 때문에 Rule XALQ를 사용할 수 없다. Function P2010도 Schema에서 수정해야 사용할 수 있어진다. 


<그림> 7.34 Rule XALQ를 추가한 Schema KRT0

Standard에서 제공하는 P2010의 경우는 Par1에 X930이라는 Rule을 가지고 있다. P2010이 Rule을 가지고 설정된 경우에는 프리미엄 관련된 값이 IT로 전송되지 않는다. 


<그림> 7.35 급여계산 로그

임금 유형 2010(연장수당)에는 금액만이 보일 뿐 프리미엄 관련된 필드는 보이지 않는다. Rule XALQ에서는 테이블 ALP에 있는 값을 조회하지만, ALP 역시 생성되지 않기 때문에 의미가 없게 된다.

<그림> 7.37 수정된 P2010으로 처리된 로그

기존에는 없던 '01 X 01001'이라는 정보가 추가된 것을 알 수 있다. 내부적으로 ALP라는 테이블에 해당 2010(연장수당)의 프리미엄 값이 저장되고 IT에는 ALZNR이라는 필드에 '01'이라는 값이 저장되게 된다. ALP 테이블의 ALZNR에도 '01'이라는 값이 저장되게 된다. 서로 연결고리가 되는 것이다.


<그림> 7.38 수정된 P2010 이후 Rule XALQ 내역

BETPE 필드부분에 '500'이라는 부분이 보일 것이다. 프리미엄 설정에서 01의 경우는 금액 필드에 500을 넣어두었고 Rule XALQ에서는 금액 필드를 조회하여 비율필드에 넣는 규칙으로 처리된 것을 이해할 수 있다. 

프리미엄을 처리하는 두 번째 방법은, 시간 임금 유형을 급여 계산 시에 처리하는 방법에 대해서 이해해야 한다. 시간 임금 유형을 시간 수만 입력하여 급여 계산 시 단가를 산정 지급 금액을 생성하는 방법, 그리고 시간 수/금액을 같이 입력하여 시간 수는 단순 정보성으로만 처리하고, 입력한 금액으로 처리하는 방법 두 가지로 구분할 수 있다. 전자의 경우에는 해당 임금 유형 속성 중 테이블 T512W 에 평가 기준에 값이 있어야, 해당 단가를 이용하여 금액을 만들어 낼 수 있다. 이와 같이 평가 기준(T512w-GVBLA)에 값이 있는 경우는 프리미엄의 첫 번째 방법과 같이 P2010에 Par1 값을 없애는 것이 아니라, 그래도 X930을 사용하여 처리할 수 있다. 


<그림> 7.39 평가 기준을 사용하고 X930을 이용한 내역

위 그림처럼 2010(연장수당) 하나 더 생기는 것을 알 수 있다. 이런 부분은 해당 Rule을 수정하여 사용자가 원하는 방식으로 처리해야 할 것이다.

<그림> 7.41 초과근무 보상 유형 상세 내역
Standard에서 제공하는 것은 총 4가지로 초과근무 보상 유형을 이용하지 않는 경우는 공백인 '임금 유형의존'을 선택을 하면 되고, 화면에서도 기본 값으로 처리된다. 사용자가 추가적인 유형을 만들고자 하면, 이하의 내용을 이해하고 추가할 수 있다. 

급여에서 처리되는 초과근무 보상 유형 방식은 두 가지로 구분할 수 있다. Schema KRT0를 살펴보면 DAYPR TC00라는 부분이 있다. Schema TC00를 호출하는 것으로 시간 평가와 같은 효과를 내는 수준의 schema이다. 하지만, Infotype 2001, 2002, 2005를 이용하여 처리하는 방식이라 2010을 조회하지는 않는다. 물론 위 인포타입을 사용하여 처리하게 되면 Schema TC00 내의 Rule TC00를 통해서 초과근무 보상 유형을 사용할 수 있다. 

두 번째 방법은 시간 평가를 사용하지 않고, 급여로만 처리하는 방법이다. 이 경우에는 프리미엄의 두 번째 처리 방법처럼 평가 기준을 사용하는 것이다. 

<그림> 7.42 초과근무 보상 유형 처리 내역

 SUBRC 2와 Rule X933까지의 진행은 같고, Rule X933에서 호봉그룹/단계를 사용하지 않으며, 포지션/작업장을 사용하는 경우이나, 해당 포지션/작업자의 금액이 없는 경우, 변수 테이블인 VAR에서 PK의 값이 0보다 큰 경우 SUBRC 3로 Rule X934로 넘어가게 된다.
	- SUBRC 4
 SUBRC 3와 같으나, 변수 테이블인 VAR에서 PK의 값이 0인 경우에 SUBRC 4로 Rule X934로 넘어가게 된다.
	- SUBRC 5
SUBRC 2와 같으나, 포지션/작업장의 금액이 있는 경우에 SUBRC 5로 Rule X934로 넘어가게 된다.

SAP에서는 휴가 사용 일수를 쿼터라는 개념으로 관리한다. 시간 평가 혹은 사용자의 직접 입력 방식을 통해서 Infotype 2006(휴무쿼터)에 생성할 수 있고 해당 쿼터별로 사용 가능 기간이 관리가 되어, 사용자가 Infotype 2001(휴무)에서 연차휴가(물론 해당 근태 유형과 쿼터는 서로 지정이 되어 있어야 한다.) 사용하게 되면, 자동으로 쿼터 수가 제어되어 공제가 시작된다. 사용하고 남은 잔여 연차쿼터에 대해서는 회사마다 다른 규정에 근거하여 보상을 시도하게 된다. 이 경우에 Standard를 활용할 수 있는 방법과 단순히 임금 유형에 해당 금액을 입력하여 지급하는 방법으로 구분해 볼 수 있다. 

1) Standard 활용 방법
Infotype 2006(휴무쿼터)에 잔여 쿼터가 남은 경우, PC00_M41_LQC0(휴가쿼터 보상 생성)을 이용하여 Infotype 0416(시간쿼터 보상)으로 전송하여, 급여 계산으로 지급

2) 단순 처리 방법
Infotype 2006(휴무쿼터)에 잔여 쿼터가 남은 경우 해당 쿼터 수를 조회하여 사용자 혹은 프로그램으로 Infotype 0015(추가지급)에 해당 임금 유형과 보상금액을 입력하여 급여 계산으로 지급

1)의 경우는 Standard 프로그램을 활용하는 방법이라, 각 회사의 보상 방법과 상이할 가능성이 있지만, 잔여쿼터에 대한 처리가 정확하게 이루어진다고 볼 수 있다.
2)의 경우는 각 회사의 보상 방법에 근거하여 처리할 수 있으나 사용자가 단순 입력을 하는 경우는 Infotype 2006(휴무쿼터)에 잔여 쿼터 수가 남아 있게 되고, 프로그램을 CBO로 구성하여 처리하는 경우는 Infotype 2006(휴무쿼터)의 잔여 쿼터 수를 처리해주는 부분에 신경을 써야 한다. 

시간 한도 보상방법 정의에서는 Standard를 활용할 경우에 Infotype 2006(휴무쿼터)와 Infotype 0416(시간쿼터보상)을 연결해주는 보상 방법에 대해서 설정하는 IMG이다.

위 그림에서 보이는 것처럼 T521B 테이블에 해당 내역이 없다고 나오게 된다. 수취인 결정 테이블이 T521B에서 관리되기 때문이다.


<그림> 7.59 동호회 유형과 수취인이 정상적인 경우
동호회 유형과 수취인이 제대로 입력되는 경우는 해당 수취인의 정보가 관련 필드에 기본값으로 나타나게 되고 저장도 가능해진다. 실제로 수취인 키에서 입력 가능 엔트리를 선택하게 되면 지정된 수취인 키만 보이기 때문에 잘못 입력되어 저장될 수는 없다.


<그림> 7.60 수취인 키 필드의 입력 가능 엔트리

수취인 키에서 입력 가능한 엔트리가 노동조합의 경우에는 하나만 나타나게 되는 것을 알 수 있다. 

이상으로 인사관리 이하의 급여 관련 IMG에 대해서 알아보았다. 다른 많은 메뉴는 일반적으로 한국 급여에서는 사용하지 않기 때문에 여기까지만 진행하도록 하겠다.
