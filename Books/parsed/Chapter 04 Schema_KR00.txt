정연홍

지금까지 알아 본 내용을 바탕으로 한국 급여 계산을 지원하는 'KR00'라는 스키마를 분석해보고 이를 통해 각자의 회사에 맞게 적절하게 커스터마이징해 볼 수 있도록 하자.

Chapter 4. Schema 'KR00' 

▶ Overview 
급여를 계산하기 위해서 급여 계산 드라이버1라는 프로그램을 이용하고, 그 프로그램은 급여의 상세한 처리 내용을 담고 있는 스키마를 이용하여 계산하게 된다. 스키마 중에서 한국 급여에서 사용되는 KR00를 자세히 분석해보겠다.


<그림> 4.1 Schema 'KR00'의 전체 내역
기본적으로 스키마를 조회하는 곳은 PE01이므로 해당 화면에서 조회해보도록 하자. 위 화면은 ECC6.0 버전의 내용을 캡쳐한 것이므로 버전이 다르거나 Support Package가 다르다면 차이가 있을 수 있다. 

Schmea KR00 이해에 있어 중요한 점은 것은 인포타입에서 읽어온, 혹은 급여에 관련된 테이블에서 읽어온 정보, 임금 유형이 어떻게 흘러가고, 어떤 식으로 계산되고, 결과로 저장되어가는지 이전 단계에서 저장된 결과가 어떻게 다시 활용되는지를 아는 것이다. 간단히 말하면 수많은 로직으로 구성된 프로그램 코드의 집합이 스키마이고, 그중에서도 한국 급여를 계산하는 것이 'KR00'이다.

<그림> 4.3 Function 'PGM' 조회 내역

서식 루틴 이름은 표준 이름과 자체 정의로 구분될 수 있다. 일반적으로는 Function인 경우는 'FU'+해당 이름, Operation인 경우는 'OP'+해당 이름으로 표준 이름을 구성한다. 위 경우에는 자체 정의에 DUMMY로 되어 있는 것을 알 수 있다. DUMMY인 경우는 실제 자체 로직으로 실행되는 것이 아니라, 스키마상에서 설정된 매개 변수와 함께 변수에 저장되어 급여 계산 시에 활용된다. PGM의 경우는 fc라는 내부 테이블에 설정된다. 

PGM의 경우 스키마를 실행할 때 처리되지 않고, 그 이전에 스키마를 조회하여 실행 가능한 형태로 구성할 때에 fc라는 내부 테이블에 유형별로 값이 저장된다. Include 'RPUSCF10'에서 취합된 스키마를 점검하는 로직이 있는 위치에 'PERFORM CHECK_SPECIAL.' 부분에서 PGM이 처리된다. 
*---------------------------------------------------------------------*
*       FORM CHECK_PGM                                                *
*---------------------------------------------------------------------*
FORM CHECK_PGM.

  S = STACK-STRUC.
  IF S-STRU1 EQ S_NO.
    S-STRU1 = S_FU.
    STACK-STRUC = S.
    MODIFY STACK INDEX STUFE.
  ENDIF.
  IF MODUS EQ MODUS_GEN.
    PERFORM GEN_PGM.
  ENDIF.
* F#r abschliessende Tests
  PERFORM STORE_TEST.                            "QFLK11K076043
ENDFORM.<소스> 4.1 PGM 관련 source(include RPUSCF20)

<그림> 4.6 Function UPD 내역

Function 'PGM'와 마찬가지로 DUMMY 타입이다. 역할은 급여 결과를 데이터베이스에 저장할 것인지, 단순 계산만 해볼 것인지에 대한 여부를 결정한다. 관련된 내부 테이블 fc-sw_upd에 해당 내역이 저장된다. Schema 'KR00'는 기본값이 UPD YES로, 실제로 데이터베이스에 저장한다. 하지만, 급여 계산 드라이버에서는 테스트 실행이라는 옵션으로 UPD의 기능을 무효화할 수 도 있다.

<그림> 4.8 CHECK ABR 과 관련된 에러 내역

'CHECK ABR'의 경우는 해당 클라이언트가 운영인지, 개발인지의 제어 레코드에 따라 급여가 계산되도록 제어해주는 역할을 한다. 클라이언트의 정보는 Table T000에서 관리된다. T000에서 ccategory라는 필드의 정보로 운영과 개발을 구분한다. 운영 클라이언트에서는 급여 제어 레코드와 급여 계산 기간이 맞지 않으면 다음과 같은 에러가 발생한다.

▶ Function 'PARTT'
일할 계산을 위한 일할 항목을 PSP라는 내용을 가지고 생성한다. 실제로 생성되는 항목을 이용하여 일할 계산 임금 유형을 생성하기 때문에 일할 계산에 영향을 주는 Function인 셈이다. 어떤 항목이 생성되고, 어떤 의미가 있는지 확인해보자. 항목에는 3가지 유형이 있다.

KSOLL(Calendar days), ASOLL(Workdays), SSOLL(Working hours)
Table PSP의 데이터를 기초로 하여 해당 WPBP 기간별 데이터와 전체 기간에 대한 데이터로 구성된다. 기간별 데이터는 TKSOLL과 같이 T가 시작문자 형태로 사용되고, 전체 기간에 대한 데이터는 GKSOLL와 같이 G가 시작 문자 형태로 사용된다.

KDIVI(Calendar days), ADIVI(Workdays), SDIVI(Working hours)
해당 급여 기간의 실제 달력 일수 혹은 근무 일수를 저장한다. 추후 일할 계산 진행 시에 분모에 해당하는 역할이다.

KDIVP(Calendar days), ADIVP(Workdays), SDIVP(Working hours)
위의 항목과 다르게 DIVP 변수들은 이미 정해져 있는 값을 가져온다. KDIVP, ADIVP의 경우는 Table 'T511K' 에 미리 설정한 값을 가져온다. SDIVP의 경우는 해당 사원의 Infotype 0008(기본급)의 DIVGV라는 필드의 값을 가져온다. DIVGV는 '근무시간/기간'이라는 필드이다. 아마도 Infotype 0007 혹은 0008을 설명하면서 반드시 Infotype 0007이 먼저 생성되어야 Infotype 0008에 생기는 필드가 있다고 언급을 했을 것이다. 급여에서 중요하게 쓰이는 필드이기 때문에 꼭 Infotype 0007을 먼저 생성해야 하는 것이다. 
 
Function 'PARTT'의 경우는 항상 'GENPS' 이후에 처리되어야 한다. 'GENPS'에서 임시 테이블 'PSP'을 생성하고, 'PARTT'에서 'PSP'를 이용하여 위 변수 값을 생성하기 때문이다.

급여 계산에서 중요한 부분 중에 하나인 단가를 산정하는 역할을 하는 Rule이다. Schema 'KRT0'까지 급여 계산이 진행되면, Standard에서 제시된 'KR00'인 경우에는 Infotype 0008(기본급)의 임금 유형을 임시 테이블인 IT에 저장하게 된다. 일반적으로 시간 단가에 포함하는 임금 유형은 기본급에서 관리하는 항목 정도이다. 물론 회사에 따라 Infotype 0014(반복 지급)에서 관리하는 지급항목 중에 몇 가지 수당들이 포함되는 경우도 있다(대체로 많다.).
그리고 시간 단가에 포함해야 하는 임금 유형의 경우는 처리 클래스 '01'에 0이 아닌 다른 값을 입력해야 한다. 물론 빈 값을 입력해서도 안 된 경우에는 해당 Rule에서 에러가 발생하도록 되어 있다. Rule 'KR10'을 통과하면서 IT에는 '/001', '/003', '/004' 임금 유형이 생긴다. '/001'은 시간 단가로 활용되고, '/003'은 일급 단가로 활용된다. 물론 Standard에서 제공하는 방식이다. 단가에 대한 조정이 필요한 경우에는 이곳에서부터 수정을 가할 필요가 있을 것이다.

▶ KRDPY
Type: Function

Rule 'KRDF'에서 이연지급에 관련된 언급이 있었다. 'KRDF'는 단순히 이연지급의 기준일을 임시 테이블인 VAR에 저장한다. 이연지급은 근태 기간과 급여 기간이 달라 전월의 근태에 따라, 당월에 급여를 지급하는 경우와 같은 형태의 지급 방식이다.

예) 근태 기간: 전월 16일 ~ 당월 15일, 급여 기간: 당월 1일 ~ 당월 말일

<그림> 4.31 근태 기간과 급여 기간

그림에서 근태 기간은 ①+②, 급여 기간은 ②+③이다. 급여 계산 드라이버에서는 시간 관련 임금 유형을 ZL에서 가져오는 경우에 임의적인 근태 기간으로 가져올 수 없다.
Function IMPRT를 이용하여 'ZL'을 가져오게 된다. 이때 ②+③기간의 가져오게 된다. 이후 'ZLIT KR80 P61	AMS'를 진행하면서 ZL의 시간 임금 유형을 임시 테이블인 IT로 전송한다. 단, 처리 클래스 61번의 값에 따라서 임금 유형이 생성된다. (물론 사원 그룹핑 3의 경우는 스키마의 Rule을 변형해야 한다. Standard에서 제공해주는 것은 사원 그룹핑 2에서 이미 제공하고 있으니, 적절하게 복사하여 사용하면 된다.)

Standard에서 제공하는 임금 유형을 복사하여 사용하고자 하는 시간 임금 유형으로 생성해야 한다. 처리 클래스 61의 값을 확인해야 한다.

<그림> 4.32 Standard에서 제공하는 이연지급 임금 유형

<그림> 4.37 Rule 'KR15' 내역(사원 그룹핑 3인 경우)

금액이 이미 있으면, 그대로 전송처리 Standard에서 제공하는 단가와 계산하지 않고, 수 필드의 값이 0이 아니고, 비율(단가) 필드에 값이 있으면, 계산해서 전송 처리된다. 비율(단가) 필드에 값이 없으면, Standard가 제공하는 방식으로 진행된다. 단 Operation 'VALBS'를 거치고 결괏값에 따라 다른 규칙으로 처리된다.
Operation 'VALBS'는 해당 임금 유형의 속성 중에서 평가기준 값의 여부에 따라서 'X' 값을 표시한다. 해당 임금 유형이 평가 기준이 없으면 임시 테이블 OT로 전송한다. 평가 기준이 있으면 'Z GCY X115*' 규칙을 실행하게 된다. 

<표>
ZPersonnel calculation rule 값을 초기화한다, 이후 Rule이 Operation으로 진행하지 않고, 다음 스키마로 진행한다. (P 타입의 경우는 다음 Operation으로 진행한다.)GCYRule을 사용하여 처리하는 경우 리턴 값이 길어지게 되면, Subrule을 호출하는 방식을 사용해야 한다. 이 경우에 Subrule을 호출하는 Operation이다.</표>

Rule 'X115'에 대해 살펴보면 시간 단가와 시간 임금 유형이 어떤 식으로 실지급액을 계산하는지 이해할 수 있을 것이다. 


<그림> 4.38 Rule 'X115' 내역

Operation 'VAKEY'에 옵션으로 있는 ALZNR의 여부를 판단하는 규칙부터 시작한다. ALZNR은 대체 지급(Alternative Payment) 유무를 확인하는 것으로 시간 평가에서 생성되어야 한다. 클러스터 테이블인 B2를 조회할 때 해당 값이 있으면, ZL과 ALP 테이블이 전송된다. ALP 값에 대체 지급에 관련된 값인 ALZNR 값이 들어 있다. 

대체 지급이 없다는 가정하에 Rule 'X115'를 분석해보겠다. 일단, Rule 'X115'의 내용을 살펴보면, 'VWTCL', 'VALBS0', 'VALBS1', 'VALBS2', 'ADDNA', 'FILLF', 'WGTYP', 'NEXTR' 정도로 구성되어있는 것을 알 수 있다. 해당하는 Operation 분석을 하면, 충분히 Rule 'X115'가 이해가 될 것이다. 

VWTCL은 해당 임금 유형의 처리 클래스 코드에 따른 값을 확인하는 역할이다. VWTCL 18이므로, 임금 유형의 처리 클래스 18을 확인해야 한다. 처리 클래스 18은 위에서 언급 대체 지급에 관련된 항목이다. 대체 지급은 고려하지 않으므로, 해당 임금 유형은 값이 공백이다. 그럼 '*'로 이동해야 한다. VALBS0, VALBS1, VALBS2는 operation 'VALBS'의 다양한 옵션 형태이다. 임금 유형의 속성 중 평가 기준 임금 유형(/001, /003, /004, ...)과 같은 임금 유형의 값을 이용하여 계산을 할 수 있게 정의할 수 있는 부분이 있다. 뷰 테이블인 V_512W_B에서 '현재 임금 유형', '첫 번째 파생 임금 유형', '두 번째 파생 임금 유형'으로 정의가 가능하다. VALBS0, 1, 2는 각각 현재 임금 유형, 첫 번째 파생 임금 유형, 두 번째 파생 임금 유형의 정보를 가져오는 역할을 한다. 


<그림> 4.39 뷰 테이블 V_512W_B 내역

평가 기준에는 위 그림처럼 '01'을 사용했으면, 급여 계산 시에는 secondary wage type중 '/0' + nn인 임금 유형을 사용한다. '01'을 사용했으므로, '/001'을 사용한다. 그 밖에도 'K', 'TG', 'T'와 같은 옵션을 이용하여 다양한 값을 제공할 수 있다. 백분율의 경우는 평가 기준에서 제공하는 임금 유형에 해당 백분율만큼 가산한 단가를 활용하게 된다. 

VALBS0	ADDNA *	FILLF N	WGTYP=*	NEXTR

규칙을 다시 한번 적어보면, 일단 평가기준을 가져오게 되고, ADDNA를 사용하게 된다. ADDWT와 유사하지만, 수 필드(ANZHL)와 금액 필드(BETRG)만 누적된다. 비율 필드(BETPE)는 누적되지 않고 ADDNAE가 아니면 내부 테이블인 OT로 전송된다. 'E'인 경우는 RT로 전송된다. '*'를 사용하였으므로, 기존 임금 유형을 그대로 사용한다. 다른 임금 유형으로 저장하고 싶으면 4자리 코드를 명시해야 한다. FILLF는 ZERO=와 반대의 효과이다. FILLF 이후 수 필드(N), 금액 필드(A), 비율 필드(R)를 적용하여 내부 테이블인 OT에 해당 필드 값에 IT의 값을 저장한다. WGTYP를 통해서 해당 임금 유형으로 OT에 입력된다. 이 단계까지 오게 되면 임시 테이블인 OT에 입력되고, Rule이 마무리되면서 임시 테이블인 IT로 전송된다.

Rule 'XPPF'의 경우는 하위 Rule 'XPPP', 'XPP0', 'XPP1' 등으로 이루어져 있다. 일반적인 경우로 해당 규칙을 분석해보도록 하겠다.

<그림> 4.51 Function 'RTE'의 구조

'OOO + S + VVVVVV'로 구성된 Function이다. 이 경우 S의 경우는 매개 변수를 의미하고 그러한 매개 변수의 유형으로는 '=', '-', '+', '*' 와 같은 형태이다. VVVVVV는 총 6자리로 이루어져 있고, 총 5가지 형태로 나누어진다.

<BOX>
RTE=TSSOLLRTE-TSAU**RTE*KGENAURTE/TSDIVIADDWT*</BOX>
'RTE='는 이후에 입력된 규칙에 따라 비율필드인 BETPE에 해당 값을 입력하라는 의미이고, 이후에 나오는 TSSOLL은 T+SSOLL로 나누어 보면 Xnnnnn와 같은 구성임을 알 수 있다. 이 경우는 테이블의 필드 값이라고 정의되어 있으므로, T에 해당하는 테이블을 찾아보면 SSOLL의미는 계획된 근무시간수라는 의미이고, 해당 값은 WPBP-SSOLL에 저장된 값을 가져오게끔 되어있다. OT-BETPE <- WPBP-SSOLL의 값이 저장된다.

'RTE-'는 이후에 입력된 규칙에 따라 비율필드인 BETPE에 해당 값을 빼라는 의미이고, 이후에 나오는 TSAU**는 T+SAU**로 나누어 보면 Xnnnnn와 같은 구성임을 알 수 있다. 마찬가지로 테이블의 필드 값이라는 것을 알 수 있다. SAU**는 내부 테이블인 CABC에서 해당 내역을 가져온다. S인 경우는 CABC-S필드 값을 가져온다. 물론 ** 의 의미는 내부적으로 '00'으로 치환되어 cabc 테이블의 atype, calss, apznr 로 해당 내역을 가져온게 된다. Cabc 테이블은 Function 'PAB'를 통과하면서 휴무내역 테이블인 'AB'의 데이터를 기초로 하여 생성된다. 결근시간수라고 생각하면 된다. OT-BETPE <- WPBP-SSOLL - CABC-C (계획근무시간수 - 결근시간수)로 구성된다. OT-BETPE에는 해당 급여 기간의 실제 근무시간수가 저장된다고 생각하면 된다.

'RTE*'는 이후에 입력된 규칙에 따라 비율필드인 BETPE에 해당 값을 가산하라는 의미이고, 이후에 나오는 KGENAU는 K+GENAU로 나누어 보면 Xnnnnn와 같은 구성임을 알 수 있다. 이 경우는 테이블의 필드 값이라는 것을 알 수 있다. K인 경우는 상수값을 모아둔 T511K 테이블을 의미한다. 그 테이블에서 GENAU 변수 값을 찾아보면 해당 값이 있다. 

　　　　<그림> 4.52 T511K 테이블의 GENAU 내역

GENAU의 값은 '100,000.00'의 값을 가지고 있다. 'OT-BETPE <- ( WPBP-SSOLL - CABC-C ) X GENAU'와 같은 효과이다. 총 계획된 근무 시간 수 184시간, CABC-C의 결근 시간 수 10시간이라 가정하면 OT-BETPE에 저장된 값은 17,400,000 이라는 값이 저장되어 있을 것이다. 

'RTE/'는 이후에 입력된 규칙에 따라 비율필드인 BETPE에 해당 값을 감산하라는 의미이고, 이후에 나오는 TKDIVI는 T+KDIVI로 나누어 보면 Xnnnnn와 같은 구성임을 알 수 있다. 이 경우는 테이블의 필드 값이라는 것을 알 수 있다. KDIVI는 해당 급여 기간의 전체 달력 일수를 의미한다(사실 이 부분이 이상하다고 생각할 수 있을 것이다.). 분모에 해당하는 부분은 시간으로 계산해왔으면서, 분모에 해당하는 기준값이 시간 수가 아닌 달력 일수이기 때문이다. 아무튼, BETPE의 값을 달력 일수로 나눈다. 'OT-BETPE <- ( ( WPBP-SSOLL - CABC-C ) X GENAU ) / KDIVI'와 같은 효과이다. 

여기까지 진행을 했으면 일할 비율이 다 생성된 것이다. 'ADDWT *'는 해당 임금 유형을 다시 IT로 전송을 하는 역할이므로, 실질적인 규칙은 이 위까지라고 할 수 있다. 회사의 규칙에 따라서 실근무일수(총계획 근무일수 - 결근일수) / 달력 일수로 일할 계산을 하면 위의 분모에 해당하는 규칙 몇 개를 수정해야 할 것이다. 

▶ XVAL
Type: Rule
Rule XPPF를 통해서 /801~/816 임금 유형의 비율 필드에 해당 일할 비율이 생성되었고, 이후는 일할 처리해야 하는 임금 유형에 해당 급여 기간에 맞는 일할 임금 유형인(/801~/816)을 가산하여 일할 계산을 하는 단계이다. 일할 계산을 해야 하는 임금 유형은 처리 클래스 10에서 해당 여부를 설정해야 한다. 물론 단순히 일할 계산 처리 여부가 아닌, 일할 계산 처리 방식에 대해서는 여러 가지로 설정할 수 있게끔 되어 있다. 일할 임금 유형인 /8XX 유형이 /816까지 여러 개가 존재하는 의미가 다양한 일할 임금 유형 방식을 적용할 수 있게끔 하려는 의도이다.

일할 방식 설정은 IMG에서 진행하고, 해당 메뉴는 IMG -> 급여관리 -> 급여:한국 -> 팩토링 -> 감산인수 지정에서 해당 임금 유형에 원하는 일할 방식을 지정한다. 일반적으로는 /801로 일할하는 '1' 값을 많이 사용한다. 물론 회사마다 다양한 방식을 고수하기도 한다. 달력 일수가 아닌, 고정 30일이라든지, 실근무일수인 20일 기준이라든지, 프로젝트를 진행할 경우에는 일할 방식에 대한 적절한 협의가 필요하기도 하다.

　　　　<그림> 4.62 Subschema 'XPDD' 내역
공제 임금 유형의 경우는 총지급액보다 공제액이 큰 경우에 전체공제를 할 것인지, 가능한 금액까지만 할 것인지와 같은 처리 방법을 여러 가지로 제공하고 있다. 그와 관련하여 내부 테이블 DDNTK라는 곳에 해당 내역이 발생하고, 그 내역을 이용하여 해당 월의 IT와 RT에 내역에 조정이 들어가게 된다. 

Schema 'XPDD'의 경우는 이후 Schema 내역에 따라서 Function PRPRI에 의해서 발생되는 DDNTK를 이용하여 처리하는 방식이라, 세금 및 사회 보험료 계산이 끝난 이후의 IT 내역을 확인해야 한다. 


　　　　<그림> 4.63 세금, 사회 보험료 계산이 끝난 후의 IT 내역

/550의 경우는 총지급액(/101)에서 소득세, 주민세, 사회 보험료를 제외한 금액으로 생성된다. 모든 공제의 경우는 세금과 사회 보험료보다 우선할 수 없기 때문에 먼저 처리되고 난 후에 '법정실급여' 라는 개념으로 생성된다. 이후는 일반 공제 금액을 공제하기 위해서 총 취합이 된 순지급/공제(/110) 이라는 임금 유형의 금액이 공제되고, 그 잔액에 따라서 은행이체 혹은 마이너스 급여 형태로 처리된다. 위 그림의 경우는 '733,910' 만큼 공제가 더 큰 상태이므로 공제 임금 유형의 방식에 따라 달라질 수 있지만, 아래의 그림과 같이 내부 테이블 DDNTK, ARRRS가 발생하게 된다.


　　　　<그림> 4.64 내부 테이블 DDNTK, ARRRS 내역

Function PRPRI를 통과하면서 sw_ddntk에 값이 true('X')인 경우이면 LPBEG~LPEND사이의 Schema를 한 번 더 실행하게 된다. 내부 테이블 DDNTK의 값이 없을 때까지 진행하게 된다. 루프를 한 번 더 돌게 되고, DDNTK의 값이 존재할 때 Schema 'XPDD'에서 처리가 시작된다고 보면 된다.


<그림> 4.65 Function PPDNT 로그 내역

DDNTK에 설정된 금액만큼 IT 공제 금액을 줄여주고 있다. 이 부분은 임금 유형 7002의 속성이 가능한 범위 내까지만 공제하는 타입이기 때문에 이와 같은 형태로 처리되는 것이다.


<그림> 4.66 2번째 실행되는 PPDNT 내역

DDNTK의 로그에 따라 IT, RT, DDNTK, ARRRS 테이블이 형성되는 화면이다. IT상에는 임금 유형 7002의 경우는 -4,000,000이 아닌 공제 가능한 금액인 -3,266,090 금액이 설정되고, 이후 Schema를 진행해서, 현재 총지급액에서 공제 가능한 금액으로 변경된 것이므로, 해당 사원에게 별도로 지급할 금액이 없는 지급 금액 0인 상태로 처리될 것이다. 테이블 ARRRS 에는 공제 하지 못한 금액인 733,910 금액만큼 저장하고, 다음 달 급여에서 해당 금액을 공제할 수 있도록 처리가 될 것이다. 물론 지금의 상황은 공제 임금 유형의 공제 처리 타입이 '공제 가능한 금액'이기 때문이다. IMG에서 해당 임금 유형의 공제 방식에 대해서 설정할 수 있고, 이 부분에서 공제 유형에 대한 내역만 잠깐 살펴보도록 하겠다.

연체 공제 특성을 '1'로 한 경우는 소급 처리를 위해 증가시킨 금액만큼이 연체 테이블이 증가함을 알 수 있다. 회사마다 고유한 특성에 따라서 공제 금액에 대해서 소급을 허용하지 않는 경우도 있기 때문에 그런 경우에는 특성값을 '4'로 설정하는 것이 적절할 것이다. 1이 아닌 4를 이야기하는 것은 팀 담당자가 그런 업무 프로세스를 이해하지 못한 상태에서 해당 인포타입에서 값을 변경한 경우에 소급이 일어나게 되므로, 아예 급여 계산 시에 금액 변경으로 인한 소급이 일어나더라도 무시 처리가 될 수 있도록 '4'로 설정하는 것이 적절할 것이다. 다만, 이런 경우에 퇴직으로 인해서 추가 공제가 필요한 경우에 공제를 못할 수도 있다.

　　　　<그림> 4.72 Rule 'KR41' 내역

▶ KRSIP
Type: Function
사회보험에 대한 처리를 진행해준다. 사회보험에는 건강보험, 국민연금, 고용보험이 있고, 2008.07.01부터 노인장기요양보험까지 처리되고 있다. 사실상 회사의 사회보험 범위 경우 산재보험까지 포함된다. 하지만, 실제로 사원 기준으로 범위를 산정하게 되면, 위에 언급한 건강보험, 국민연금, 고용보험까지 이다. 산재보험은 각 사원별로 계산한다기보다는 회사 내의 전체 사원수에 따라서 산정되는 보험이기 때문에 SAP HR에서는 제공하고 있지 않다. 정리해서 이야기해보자면, 고용주가 납부해야 하는 보험에 해당하기 때문에 제외인 것이다. 

Function 'KRSIP'의 경우는 Infotype 0543(사회보험), 0544(사회 보험료)에 해당 내역이 존재해야한다. 0543의 경우는 해당 사원의 사회보험 가입 상태를 관리하고, 0544의 경우는 사회 보험료를 관리한다. 

건강보험료 산정 방식: Infotype 0544(사회 보험료)에 서브타입 '1'로 입력되어 있어야 함.


<그림> 4.73 Infotype 0544(사회 보험료) 중 건강보험료 유형

건강보험료의 경우는 '월간 보상 금액'을 입력하는 방식이다. 입력된 '월간 보상 금액'에 따라 해당 보험료 산정은 Table 'T7KRMR'에서 해당 기준일 기준으로 비율을 조회하여 계산한다. 
2008년의 건강보험료는 사원비율은 '2.540'이고, 고용주비율도 같다. 월간 보상 금액에 해당 비율을 가산하여 보면 다음과 같이 계산되는 것을 알 수 있다.
<BOX>
3,000,000(월간 보상 금액) × 2.540(건강보험료 비율) = 76,200(보험료)</BOX>
국민연금의 경우도 건강보험과 유사하다. 

　　　　<그림> 4.74 Infotype 0544(사회 보험료) 국민연금 유형

건강보험과 달리, 월간 보상 금액만 보이는 구조이다. 국민연금의 보험료 산정은 Table 'T7KRSR'에서 관리되고, 2008년의 사원 비율의 경우는 '4.500'이고, 고용주 비율도 같다. 사회보험에 대한 비율 관리는 Standard에서 제공하고 있고, Support Package나 긴급한 경우는 Notes를 통해서 제공되고 있다. IMG에서는 급여관리 -> 급여:한국 -> 사회보험 -> 보험료율에서 관리되고 있다. 

고용보험의 경우는 Infotype 0544(사회 보험료)에서 관리되고 있지 않다. 고용보험료의 경우는 고용보험료 산정 대상이 되는 임금 유형을 정확히 지정해두었다면 마치 소득세처럼 해당 산정 금액을 기준으로 Table 'T7KRSR'의 비율대로 계산을 하여 보험료를 산정한다. 즉, 소득이 없다면 고용보험료는 발생하지 않는다. 반대로 건강보험료의 경우는 소득과 무관하게 발생할 수 있다. 그래서 무급휴직과 같은 경우에는 Infotype 0543(사회보험)에서 상태 값을 조정하여 면제 처리하거나, 조정 금액을 이용하여 추후 복직 후에 공제하는 방식을 사용하기도 한다. 

고용보험료의 구성은 '실업급여', '고용안전', '직업능력' 보험료로 구성되어 있다. 이 경우에 '실업급여' 부분은 사원과 고용주가 같이 부담하고, '고용안전'과 '직업능력'의 경우는 고용주만 부담하게 된다. 실제로 고용보험료를 산정하는 대상 금액은 같지만, 사원과 고용주가 부담하는 보험료는 차이가 있다. Standard에서는 같은 비율, 즉 실업급여 부분에 대해서만 제공하고 있기 때문에 회사마다 사원의 급여 계산 시에 고용주 고용보험료 산정을 전체로 하고자 할 경우에는 비율을 관리하는 테이블의 값을 변경해야 한다. 


　　　　<그림> 4.75 국민연금 및 사원보험(한국)의 HR 프리미엄 비율 내역

고용보험 비율을 관리하는 IMG 화면이고, 고용주 보험료율은 '1.300'으로 되어있다. Standard의 경우는 사원비율과 고용주비율이 동일하게 '0.450'로 제공되지만, 임의로 비율을 조정하여 사용할 수 있다. 


　　　　<그림> 4.76 사회 보험료 계산 결과

건강보험료나 국민연금 보험료의 경우는 원 단위가 0으로 보이지만, 고용보험료의 경우는 원 단위에 0이 아닌 원 단위에 금액이 있는 것을 알 수 있다. Function 'KRSIP'에서 건강보험료와 국민연금 보험료의 경우는 원 단위 절사 처리를 내부적으로 해주지만, 고용보험료의 경우는 해당 로직이 주석으로 막혀 있어서 처리되지 않는다.


　　　　<그림> 4.77 Function 'KRSIP' 내역(원단위 절사)

소스 내역을 살펴보면 pkr99_medical, pkr99_pension의 경우는 각각 건강보험, 국민연금의 경우는 trunk 를 사용하여 원 단위는 절사 처리하고 있음을 알 수 있다.


　　　　<그림> 4.78 Function 'KRSIP' 고용보험료 절사 주석 내역

<그림> 4.78 소스 내역에서 pkr99_employment의 경우 주석으로 막혀 있는 것을 볼 수 있다. 그리고 주석에 Personnel Calculation Rule을 이용하여 처리할 수 있다고 되어 있다. 프로젝트 진행 시에 Function KRSIP 이후에 Rule을 추가하여 고용보험의 경우는 절사 처리한다. 물론 회사의 정책에 따라 원 단위 절사 없이 처리도 가능하다. 

회사의 업무 처리를 위해 사회 보험료, 특히 건강보험료의 조정을 원하는 경우가 있다. 이 경우에는 Standard에서 제공하는 임금 유형 중 'HD01', 'HD02'를 이용하여 조정을 할 수 있다. 물론 용도 자체는 공단에서 특정 사원에 대한 감면 금액이 오는 경우에 입력하는 임금 유형이긴 하지만, 입력하여 사용하게 되면, 계산된 건강보험료에서 해당 금액만큼 삭감 혹은 추가(+, -를 어떻게 입력하느냐에 따라 조정이 가능) 한 금액으로 발생하게 된다. 


<그림> 4.79 Function KRSIP 감면 로직

<그림> 4.79 중에서 PERFORM cal_med_ded_premium이라는 부분이 보일 것이다. 이 부분에서 사원 건강보험료인 ee_premium의 금액을 HD01, HD02의 금액으로 각각, 사원 및 고용주 부담분을 조정하게 된다. 

* Medical insurance temporary deduction for steep premium increasement

  CHECK krsi-subty EQ pkr99_medical.
  READ TABLE it            WITH KEY lgart = pkr99_wt_mi_ee_ded_share.
  IF sy-subrc = 0.
    p_ded_ee_premium = p_ded_ee_premium + it-betrg.
    p_ee_premium     = p_ee_premium - it-betrg.
  ENDIF.

  READ TABLE it            WITH KEY lgart = pkr99_wt_mi_er_ded_share.
  IF sy-subrc = 0.
    p_ded_er_premium = p_ded_er_premium + it-betrg.
    p_er_premium = p_er_premium - it-betrg.
  ENDIF.
　　　　<소스> 4. 2 perform cal_med_ded_premium 내역

<소스> 4.2에서 보는 것처럼 pkr99_wt_mi_ee_ded_share라는, 다소 긴 이름을 가진 내역의 값을 조회하여 보험료를 조정해준다. pkr99_wt_mi_ee_ded_share는 /171라는 임금 유형으로 HD01의 속성 중 누적 클래스 '71'에 체크되어 있어, /171에 해당 금액이 누적되고, 그 금액을 이용하여 조정하게 된다. 

단, 이 부분에서 회사마다 다르게 접근하는 경우가 발생할 수 있다. HD01을 이용하여 조정하게 되는 경우에는 건강보험료가 조정되고, 조정이 된 건강보험료를 기준으로 장기노인요양 보험료를 산정하는 방식이기 때문에 건강보험료는 조정하고 싶으나, 장기노인요양 보험료는 조정하고 싶지 않다라는 접근 방식을 가지게 되면 좀 곤란하다. 이런 경우에는 Standard에서 제공하는 조정 방식이 아닌, 별도의 조정 임금 유형을 만들고, 해당 임금 유형으로 조정하는 Rule을 구성하여 Function KRSIP이후에 추가하여 처리하는 방식이 가장 깔끔할 것이다. 일반적으로 기존 legacy에서는 소득세나 사회 보험료에 대한 조정을 쉽게 처리하던 업무 습관에서 조정이 까다로운 SAP HR을 도입하는 과정에서 위와 같은 요구가 많이 발생하기도 하지만, 업무 프로세스를 가급적이면 Standard에 맞춰가는 것도 좋은 업무 처리가 될 수가 있을 것이다. 물론 Standard가 정답이라고 이야기하는 것은 아니다. 다만, SAP HR은 솔루션 형태이므로, 솔루션의 테두리 안에서 처리하는 것이 다른 부분에 여파가 없을 수 있다는 것이다. 여러 가지 경우에 따라 해당 프로젝트 진행자나 운영자의 판단에 따라 처리할 수는 있다. 

▶ KRTAX
Type: Function

2007.07.01 이후부터 간이세액 테이블이 제공되어, 간이세액표로 소득세를 공제할 수 있게 되었다. 간이세액표의 경우는 Support Package를 통해서 업데이트가 되며, 해당 테이블은 'T7KRST'에서 관리된다. IMG 메뉴는 급여 관리 -> 급여:한국 -> 세금 -> 단순 세금 테이블 유지보수이다. 해당 IMG는 잘못된 부분이 있는 경우에 해당 레코드를 선택하여 수정하는 용도로 사용하면 된다.

해당 레코드를 선택하고 들어가면 부양가족 수에 따른 소득세 내역이 관리되고 있다.


　　　　<그림> 4.81 단순 세금 테이블 상세 내역

<그림> 4.81에서 보는 것처럼 해당 범위에 소득세 및 다자녀인 경우의 소득세가 관리되고 있고, 그에 따라 추후 Function KRTAX에서 해당 소득세 금액으로 공제 처리된다. 다자녀의 경우는 내부적으로 자녀 수를 확인하여 해당 자녀 수가 2명 이상인 경우에 f_many라는 변수를 'X' 값으로 체크하여 다자녀 공제 필드의 금액으로 처리된다.

▶ KR4A
Type: Rule

Rule 'KR4A '의 경우는 연말정산(급여사유 0005) 이후 해당 차감환급분에 대한 처리를 위해 존재하는 규칙이다. 일반적으로 연말정산의 경우는 이듬해 1월 급여 전에 계산하게 된다. SAP에서는 급여 사유 0005로 연말정산을 처리한다. 이 경우에는 차감환급분이 바로 /559와 같은 임금 유형으로 생성되는 방식이 아닌, 차감환급분이 /YAI(차감환급 소득세)와 같은 임금 유형으로 저장된다. Rule 'KR4A'에서는 직전 급여(RT)를 조회하여 해당 임금 유형을 여부에 따라, /3RI 임금 유형으로 해당 금액을 전달한다. 전달된 금액은 이후 은행이체에 반영하게 된다. /YAI -> /3RI, /YAR -> /3RR, /YAS -> /3RS 로 반영된다.

규칙의 내용을 보면 'AMT=L /YAI ADDWTI/3RI'로 구성되어 있다. 이 부분에서 AMT의 방식에서 'L'의 속성에 따라 직전 RT 내역을 조회해오도록 되어 있다.

Function 'ACTIO'의 경우는 par1에는 Rule이 존재하고, par2에는 해당 Rule을 몇 번이나 처리할 것인지를 결정하는 변수가 오게 된다. Blank인 경우는 한 번만 돌고 끝나는 방식이다. Rule 'KR4A'의 경우는 Function 'ACTIO'와 같이 사용되었고, par2가 없는 방식으로 처리되어 해당 Rule을 한번 처리하고 끝난 경우이다.

　　　　<그림> 4.83 IMG의 연체 공제 특성 내역

법적 공제 항목이 처리된 법정 실지급액 기준에서 일반 공제 항목을 처리하는 경우에 남은 지급 금액이 부족할 수 있다. 부족한 경우에 해당 공제 항목의 속성에 따라 공제 처리가 진행된다. IMG의 공제 관련된 설정에 따라 처리되는 결과는 DDNTK에 저장이 되거나 혹은 DDNTK, ARRRS 테이블에 저장된다. 

우선순위와 연체라는 항목을 설정하는 것이다. 우선순위는 여러 개의 공제 항목이 있는 경우에 법정 실지급액이 모든 공제 항목을 처리할 수 있다면 관계가 없지만, 그렇지 않은 경우에 우선순위에 근거하여 공제가 처리된다. 물론 우선순위가 하위인 경우는 공제가 처리가 안 되고, DDNTK 및 ARRRS 테이블로 저장될 수도 있다. 연체의 경우는 공제가 처리되지 않는 경우에 어떤 식으로 처리할 것인지, 지정하는 것이다. 관련된 속성은 추후 IMG 편에서 언급할 것이다. 몇 가지만 살펴보도록 하겠다. 
<표>
연체 속성 1
공제 총액해당하는 공제 항목의 전액을 공제하는 방식연체 속성 2
공제 가능액해당하는 공제 항목의 금액 중 공제 가능한 금액만 공제 나머지는 처리되지 않음연체 속성 3
연체금 테이블에 나머지 작성이 경우에 ARRRS 테이블에 저장되고 다음 급여 계산시에 처리됨연체 속성 5
전체 공제 또는 공제 안 함해당하는 공제 항목의 전체 금액을 공제하지 못하는 경우에는 공제하지 않음</표>

연체 속성 1과 연체 속성 3 차이는 단순히 ARRRS 테이블에 생성되고 안 되고가 아니라, 연체 속성 1은 전체 금액을 공제한 방식이기 때문에 법정 실지급액이 사실상 마이너스가 되고, 그로 인해서 /561(청구)라는 임금 유형이 발생하게 된다. 회사마다 청구 즉 급여 자체가 마이너스 발생을 원치 않는 경우도 있을 수 있다. 물론 청구가 발생하는 경우는 다음 달 급여에서 /563(전월에서 이월)이라는 임금 유형으로 변경되면서 공제 처리가 다시 이루어지게 된다. 위에서 언급한 것처럼 마이너스 급여가 발생하는 것을 원치 않는 경우에는 연체 속성 3을 이용하여 연체금 테이블에 저장하게 되면 법정 실지급액이 0이 되어 이체할 금액도 없고, 마이너스 급여로 발생하지도 않게 된다. 다만, 연체금 테이블에 저장되어, 다음 달 급여에서 공제 잔액에 대한 처리가 진행되게 된다.

<그림> 4.85에서 '본사상조회'라는 임금 항목의 금액이 '4,400,000'이지만, 법정 실지급액은 '3,039,290' 으로 '1,360,710'만큼 부족한 것을 알 수 있다. 연체 속성을 3으로 하였기 때문에 공제 가능한 금액만큼 공제 처리하고 나머지 금액에 대해서는 DDNTK, ARRRS에 저장하게 된다.

<그림> 4.89 두 번째 루프 시 Function PRPRI 내역
Function PRDNT에서 DDNTK 내역에 따라서 공제 가능한 금액으로 변경하게 되고, 두번째 루프의 PRPRI의 로그가 조금 달라진 것을 알 수 있다. 본사상조회의 원 금액은 '4,400,000' 이지만, PRDNT를 진행하면서 해당 금액이 법정 실지급액과 같은 '3,039,290'으로 변경되어, 공제 처리가 완료된다. DDNTK에는 더 이상 공제를 위한 항목이 존재하지 않는다고 나오고, 더 이상의 루프는 없다. 공제하지 못한 잔액은 ARRRS에 저장되어 다음 달 급여에서 처리될 것이다. 

▶ X040
Type: Rule

공제 항목에 대해 처리되면 Rule 'X040'을 통해서 법정 실급여에서 실급여(/560)가 발생하게 된다. Function PIT를 통해서 처리되는 부분이라, 이 부분의 IT에는 법정 실급여(/550)와 일반 공제 금액의 합계인 순지급/공제(/110)라는 임금 유형이 남게 된다. 법정 실급여에서 일반 공제 금액을 공제하게 되면 실제로 은행에 이체하는 금액이 발생하게 되는 것이다.

물론 은행이체는 /559 임금 유형을 사용하지만 바로 변경되기 전의 임금 유형이 실급여(/560)인 것이다.

<그림> 4.94 Schema 'XRR0' 내역

▣ 목적
SAP에서 소급 방식에 대한 이해가 필요한 부분이다. 일반적인 legacy 시스템에서의 소급은 전월에 지급하지 못하거나 공제하지 못한 내역을 단순히 당월에 반영하는 전월 내역이라는 구분을 명확하게 할 수 없는 구조가 많다. 임의로 전월 급여 내역에 반영을 한다든가, 별도의 테이블에 추가적인 작업을 하는 경우가 많다. SAP에서의 소급은 지급이나 공제 내역을 해당 인포타입에 원인이 발생한 기간 혹은 지급일 기준으로 입력하게 되면 당월 급여 계산 이전에 소급이 발생된 월의 급여에 대해서 전체적으로 재계산을 진행한다. 그리고 이전에 계산된 내역과 비교하여 소급으로 인한 재계산 차이를 당월 급여로 전달하여 소급으로 인한 처리를 반영하게 된다. 이런 진행을 통해서 소급 발생 월의 경우는 최초 계산된 내역과 소급으로 인한 재계산 내역이 각각 급여 결과 테이블에 저장된다. 이런 방식으로 평균 임금을 계산할 경우에도 별다른 조치 없이 새로 계산된 내역이 자연스럽게 반영된다는 장점이 있다.

▣ 설명

외부이체는 회사에서 제공하는 기숙사비에 대한 공제 후 내역을 별도의 수취인으로 처리하고자 할 경우에 사용한다. 사원에게 추가 지급을 하기 위해서 사용하는 것이 아닌, 동호회비와 같은 용도로 사용될 수 있을 것이다. 물론 동호회비의 경우는 이미 Infotype 0057(회비)로 사용하는 것이 적절하다 할 수 있다. <그림> 4.101 Infotype 0011(외부이체) 처리 흐름

외부이체 처리는 Infotype 0011(외부이체)에 저장된 내역을 임시 테이블인 IT와 BT로 전달하는 과정부터 시작된다.


<그림> 4.102 Rule X055 출력 로그 화면

Infotype 0011(외부이체)에서 조회된 기타공제-식당(7107) 임금 항목 내역을 IT와 BT에 생성한다. IT와 BT에 생성될 때 서로 해당 정보를 연결하기 위한 '01' 이라는 값을 가지게 된다. BTZNR이라는 필드 값을 서로 연결고리로 사용하게 된다. 기타공제-식당(7107)이 입력되면서 IT에서는 '지급액 밸런스(/562)'의 금액을 기타공제-식당(7107) 금액만큼 조정한다. 

다음 규칙인 X045는 기타공제-식당(7107)의 처리 클래스 속성에 맞게 RT로 전송하는 역할을 한다. 처리 클래스 25번의 속성을 '1'로 해야 RT로 전송된다. 0으로 하게 되면 에러가 발생한다. 


<그림> 4.103 처리 클래스25 속성을 0으로 지정한 경우

규칙 X070의 경우는 임시 테이블인 IT에(급여 계산 마무리 단계에서) 내역이 있는 경우 에러를 발생시키는 역할이다. 처리 클래스 25의 속성을 0으로 하게 되면 규칙 X045에서 RT로 전송되지 않고, IT에 남아있게 되어 에러가 발생하게 된다. 


<그림> 4.104 Rule X045 출력 로그

기타공제-식당(7107)의 누적클래스 10이 체크되어 있어서 순지급/공제(/110)에 금액이 발생하게 되고, 기타공제-식당(7107)은 RT로 전송된 이후 IT 내역이다

실급여(/560) 금액은 당월 급여 계산을 통해서 산출된 금액이다. 이 부분에서 외부이체로 인해서 조정이 필요하고, 실질적으로 조정될 경우의 금액이 지급액밸런스(/562) 금액이 조절될 금액이다. 규칙 X047은 임금 유형 중 순지급/공제(/110)과 실급여(/560)만 처리되게끔 된 고정형 규칙이다. 절대적으로 순지급/공제(/110)이 있어야 정확하게 사용될 수 있는 구조를 가지고 있다. 순지급/공제(110)으로, 실급여(/560), 지급액밸런스(/562)를 조정하고, 실급여(/560) 금액은 외부이체로 처리되는 금액만큼 줄어들게 된다. 이후 줄어든 실급여(/560)으로 은행이체(/559)를 발생하게 된다. 순지급/공제(/110)은 RT로 전송되어 누적된다.


<그림> 4.105 Rule X047 출력 로그 

순지급/공제(/110)은 RT로 전송 처리되어 임시 테이블인 IT에서 제외되어 있고, 해당 금액만큼 실급여(/560)의 금액이 줄어든 것을 알 수 있다. 외부이체를 통해서 처리는 여기까지 이다. 결국, 은행이체를 위한 금액에서 외부이체로 처리하기 위해서 실급여 금액을 줄이고, 은행이체 테이블인 BT에 해당 내역을 발생시키는 과정을 통해서 처리되는 것이다. 

▶ X050 
Type: Rule

규칙 X050에서는 Infotype 0009(은행이체)의 은행정보를 이용하여 해당 사원의 급여 이체 내역을 생성하게 된다. Infotype 0009의 유형에 따라 몇 개의 은행 정보를 관리할 수 있고, 동적으로 이체 금액을 관리할 수도 있다. 하지만, 일반적으로 회사에서는 이체 금액 중 몇%만 다른 은행으로 이런 방식이 아닌, 특정 임금 유형에 대해서는 별도의 계좌로 입금받고 싶다는 요구가 많다. 하지만, SAP에서 제공해주는 방식은 전체 금액 중 얼만큼만 다른 은행으로 이체하는 방식이라 일반적으로 프로젝트 진행 시에 원하는 방식과는 다르기 때문에 급여 이체의 경우는 단일 계좌를 권고한다. 물론 회계의 사원밴더마스터를 생성하기 위한 별도 계좌의 경우는 Infotype 0009(은행이체)의 서브타입으로 관리하고, 회계측과 협의하여 해당 계좌를 조회하는 것으로 결정하면 된다. 출장비나 기타 별도 지급 처리되는 금액에 대해서는 주거래 은행이 아닌 추가 관리하는 유형으로 처리하는 방식이 가능하다. 서브타입의 경우는 '0'과 '1'로 사용을 하게 된다. 1을 사용하는 경우에는 이체를 위한 고정금액이나, 비율을 입력해야 한다. 단순 정보성으로 사용하기 위해서는 다른 서브타입을 사용해야 한다. 단, 금액을 사용하는 경우에 해당 월의 급여가 서브타입 1에 설정해둔 금액보다 적으면, 서브타입 0의 계좌로는 이체 금액이 없이 전액 1의 계좌로 이체된다. 


<그림> 4.106 Rule X050 내역

이전 단계의 IT 내역을 보면 실급여(/560)과 지급액밸런스(/562)가 세트로 구성되어 있는 것을 알 수 있다. 사실 어떻게 보면, 불필요하게 같은 정보를 두 곳에 담아두고 있다고 생각할 수 있다. 왜 두 곳에 담아왔는지가 규칙 X050에서 알 수 있다. 은행이체 계좌가 하나라면 사실 큰 의미가 없지만, 하나 이상에서는 지급액밸런스(/562)에서 해당 이체 금액을 처리하고, 남은 금액을 주거래 은행 계좌로 전달하기 위해서 관리 차원에서 필요하다. 규칙 X050의 마지막 처리 내용이 'SUBWT /562' 처음에 있던 금액에서 이체한 금액을 차감하여 지급액 밸런스에 관리하여, 하나 이상의 계좌에 해당 금액을 넘겨주는 방법이다.
Z GCY X0509 -> 규칙 내에서 다른 규칙을 호출할 때 사용하는 GCY이고, 마지막 자리의 '9'는 사원그룹핑 값을 의미해서 X050의 사원그룹핑 9로 호출하는 방식이다. 사원그룹핑 9의 내역에서 operation BTREC를 통해서 은행이체 내역인 BT 테이블에 저장하게 된다. BTREC에서 T511P 테이블의 변수 중 MAXBT의 값을 이용하여 한도가 넘는 경우가 에러가 나게끔 되어 있다. 만약 회사의 은행이체 금액이 10,000,000이 넘지 않고, 넘는 경우를 체크하고자 하면, MAXBT 값을 조정하면 된다.

▶ X060
Type: Rule

규칙 X050을 통해서 BT를 생성하면, 은행이체(/559)가 생성된다. 급여 계산으로 처리될 내용들은 다 나온 것이고, 마지막으로 임시 테이블인 IT 내역을 정리하는 규칙이 X060이다


<그림> 4.107 Rule X060 입력 로그

은행이체(/559)이 생성된 것이 보이고, 지급액밸런스(/562)의 금액이 없는 것이 보일것 이다. 규칙 X050을 통해서 지급액밸런스(/562)으로 이체 금액을 만들면서 조정되어 결국 0이 된 형태이다.


<그림> 4.108 Rule X060 내역

규칙 X060의 경우는 이미 사용될 임금 유형들이 정해져 있는 방식이다. 이 단계에서 정상적으로 처리되면 발생할 수 있는 임금 유형들로 정해져 있다. 임금 유형에 따라 RT로 저장되거나 삭제된다. 이후에는 IT에는 임금 항목 내역이 남아 있지 않고, 빈 테이블이 된다.

▣ Rule, Operation, Function 설명
▶ X070
Type: Rule

Function PIT를 이용하여 처리되는 Rule이라, 만약 임시 테이블인 IT에 내용이 남아 있으면, PIT를 통해서 Rule을 진행하게 되고, 그렇게 되면, 에러가 나는 구조이다. 이 단계까지 왔을 때에는 급여의 최종적인 단계이므로, 임시 테이블인 IT에는 남아있는 내역이 없어야 한다. 

▶ EXPRT
Type: Function

최종적으로 급여 계산이 마무리되면 단순히 급여 결과인 RT 내역만 클러스터 테이블로 저장되는 것이 아니다. RT 외에도 많은 테이블들이 존재하고 있고, 각각 그 쓰임새가 있는 것이다. 추후 전표 전기를 위해서 사용되기도 한다. EXPRT는 그런 테이블을 클러스터 테이블로 전송하는 역할을 담당한다. 물론 Par2에 의한 변수 값에 따라 다른 방식으로 처리될 수 있다.


<그림> 4.110 EXPRT의 로그 내역

입력 화면을 보면 WPBP부터 BENTAB까지 17개 정도의 테이블 내역을 전송하는 역할하고 있다. WPBP, RT, CRT는 가장 기본적으로 처리되는 항목이고, ARRRS, DDNTK는 공제 임금 유형에 대한 처리로 나온 항목이다. 

몇 가지 항목에 대해서만 이야기해보자면, WPBP는 급여 계산 시 가장 중요한 항목이다. 급여 계산을 위해서는 Infotype 0000(발령), 0001(조직 지정), 0007(계획 근무), 0008(기본급)으로 해당 급여 기간에 어떤 발령이, 어떤 조직, 어느 코스트센터를 사용하는지에 따라 급여 계산에 영향을 주게 된다. 물론 이후 전표 처리 시에도 관련된다. RT의 경우는 이미 알고 있는 것처럼 급여 계산 결과 내역이 저장된다. CRT는 RT의 내역을 기준으로 연말정산에 관련된 임금 항목 누적 결과를 저장한다. BT는 은행이체를 위해서 Infotype 0009(은행이체)의 은행 정보와 급여 계산 시에 은행이체(/559) 임금 항목이 생기는 경우에 발생하게 된다. 위 로그의 경우는 공제 금액의 영향으로 은행이체(/559)가 없는 경우이고, 은행이체 금액이 있지만, Infotype 0009(은행이체)가 없는 경우 /560이라는 임금 유형이 발생하게 된다. C0는 WPBP가 발생할 때에 언급하지 않는 인포타입 하나가 있다. Infotype 0027(비용 배분)이 그것이다. 이미 모든 사원은 특정 코스트센터가 지정되어있다. 소속된 조직으로부터 지정되어 있는 값이 있지만, 특별한 경우 파견을 간다든가, 특별한 TFT 팀에 소속된다든가 할 경우 별도의 코스트센터는 물론 다른 WBS도 가능하다. 이런 경우에 Infotype 0027(비용 배분)에 해당 정보 및 기간을 입력하게 되면 C0라는 테이블이 발생하게 된다. 이후 전표 처리 시 WPBP의 내역이 무시되고, C0의 정보를 이용하여 전표가 처리된다. C1은 C0와 유사한 역할을 하지만, 다른 내역이다. C0이 전체 비용에 대한 귀속 여부를 변경한다면 C1은 특정 임금 유형에 대해서 비용 처리를 변경한다. Infotype 0014, 0015, 0267의 화면을 보면 '비용 지정'이라는 기능을 이용하여 해당 임금 항목에 대한 비용 귀속을 처리할 수 있다. 특정 임금 항목의 경우는 별도의 TFT 팀이나, 프로젝트로 인한 발생인 경우 처리할 수 있다. 

Function EXPRT의 변수 내역에 따라서 다른 처리 결과를 나타낼 수 있다. EXPRT가 가지는 Par2의 값에는 'QBE', 'ZL', 'ES', 'KR'이 있고, Par3에는 'SP'라는 값을 가지고 있다. 급여 계산에서는 Par2에 'KR' 값을 이용하여 저장하는 방식을 사용하고 있다. 

▣ 기타 관련 내용
Function EXPRT를 통해 저장된 내역은 PC_PAYRESULT를 이용하여 조회할 수 있다.
